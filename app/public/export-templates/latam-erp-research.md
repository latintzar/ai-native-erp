# Rocoto: ERP shortlist for Mexican / LATAM food-and-beverage wholesale distribution

**Checked:** 2026-08-31.  **Scope:** small/medium suppliers that sell food or beverages to restaurants, hotels, cafés and similar trade customers. This is not a restaurant-POS shortlist. Sources below are vendor-owned official pages/documentation only. A capability is “documented” only where linked; it is not evidence that Rocoto has a working integration.

## Decision framing

The recurring exchange needs are: customer master data; product/SKU and units; customer price lists; a sales order and a delivery/remisión/albarán before (or linked to) invoice; stock movement/adjustment; and, where relevant, batch/lot and expiry. “Browser” means the vendor expressly offers cloud/web operation or its product documentation is for its hosted app. A published **write API** is distinct from an import screen.

## Shortlist order and safe claims

1. **Bind ERP** is the primary Mexico candidate because official case material connects it to food production/wholesale and hospitality distribution, and its public API documentation makes an API-key test possible. This does **not** prove lot/expiry, variable-weight or delivery-route support.
2. **Alegra México** is the lowest-friction local repeatable trial: 15 days/no card, published Mexican imports and stated public API. Food-supplier use and API record-level coverage remain unproven until tenant testing.
3. **ERPNext/Frappe Cloud** is the cleanest functional QA baseline: public write API, import templates, price lists by UOM, batches and explicit delivery-note/invoice flow. It needs more setup and its Mexico operational fit is not established.
4. **Odoo** is the richest food-distribution functional match and has Mexico localization, but public write API is explicitly a Custom-plan feature. Use it to validate the data model, not as a frictionless integration target.

Do not describe any as “commonly used” or “popular among restaurant suppliers”: the sources above support capabilities, target positioning, and only the Bind case-study uses explicitly identified food/hospitality trade businesses.

## Recommended export shape before any integration claim

Maintain a vendor-neutral staging set: `customer_external_id`, legal/display name, RFC/tax ID, contact/address; `sku`, description, stock UOM, sales UOM/conversion, pack; `price_list_external_id`, customer, SKU, price, currency, validity; and a transaction header/line structure with external order ID, requested/delivered quantity, UOM, warehouse, lot/expiry only when proven. Map the vendor’s exact downloaded schema per tenant; do not assume field names or tax behavior from this review.

## Evidence gaps deliberately left open

- No official source reviewed proves delivery **routes**, driver/mobile proof-of-delivery, catch-weight/variable-weight pricing, or lot/expiry for the Mexican SaaS candidates Bind, Alegra, or CONTPAQi Vende.
- No public confirmation was found that CONTPAQi Vende exposes a write API, nor that its 20-day trial includes the paid sales/inventory modules needed for distribution testing.
- Zoho Inventory’s Mexico tax/local availability and plan entitlement for the desired batch features require a trial check.
- Odoo’s external API is plan-gated; a standard hosted plan must not be represented as API-enabled.
- Holded is included only as a Spain comparator. Its documentation does not establish Mexican/LATAM suitability.

## Cadence QA: daily distribution workflow (no accounts/payments)

Use a disposable tenant, fictional customers/items and a dedicated test user. Stop at order, stock and delivery/invoice status: do **not** create payment, collection, accounts-receivable or payment-receipt records. Record vendor record ID, external ID, timestamp, stock-before/after and visible error at each step.

| Sequence | Test action and required observation | Current evidence / blocker |
|---|---|---|

### Bsale API-access correction (supersedes prior trial wording; checked 2026-08-31)

The [Bsale API first-steps page](https://docs.bsale.dev/get-started/) links its **self-service API sandbox** account creation to [account.bsale.dev/users/create](https://account.bsale.dev/users/create). Its published account creation requires email validation. The API source does **not** state that this sandbox is the generic commercial 30-day trial, nor does it establish its duration or require a phone number; do not conflate it with `signup.bsale.io`.

Per [Bsale OAuth production documentation](https://docs.bsale.dev/oauth/), production customer OAuth is a different environment: the integrator must submit the vendor form and receive `app_id`/integrator credentials; `usrToken` is assigned to the integrator. Therefore the cascade is: **sandbox read/write test = tier 1 self-service own account/token; production customer OAuth = tier 2 self-service only after integrator/developer approval.** Apply that distinction separately to customers, products, tariffs, documents/guides and stock operations. A production token alone is not evidence that any particular operation is approved or schema-complete.
